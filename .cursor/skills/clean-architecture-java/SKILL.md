# Clean Architecture для Java

## Когда применять этот скилл

- **Архитектурные решения**: проектирование модулей/слоёв Java‑приложения, выбор границ между доменом, инфраструктурой и фреймворками.
- **Рефакторинг**: существующий код «расползся» по слоям, бизнес‑правила завязаны на Spring, JPA, веб‑фреймворки.
- **Новые фичи**: требуется добавить функциональность так, чтобы не усложнять поддержку и не ломать архитектуру.
- **Замена инфраструктуры**: смена БД, транспорта, UI, протокола без переписывания доменных правил.

## Базовые принципы

- **Правило зависимостей**  
  Зависимости в исходном коде всегда направлены **внутрь**, к более стабильным и высокоуровневым политикам.
  - Внутренние круги **не знают** о внешних (UI, БД, фреймворки, протоколы).
  - Доменные сущности и use case‑ы не импортируют классы фреймворков и инфраструктуры.

- **Слои (от центра к периферии)**  
  - **Entities (сущности)**: наиболее стабильные бизнес‑объекты и инварианты. Минимум зависимостей, максимум смысла.
  - **Use Cases / Interactors**: прикладные сценарии, оркестрация сущностей под конкретные задачи (логин, выдача токена, создание заказа).
  - **Interface Adapters**: представления (presenters), контроллеры, репозитории, мапперы DTO ↔ домен.
  - **Frameworks & Drivers**: веб‑фреймворки, ORM, драйверы БД, системы очередей, внешние API, контейнер.

- **Инверсия зависимостей (DIP)**  
  - Высокоуровневые модули **не зависят** от низкоуровневых; оба зависят от **абстракций** (интерфейсов).
  - Абстракции объявляются во внутренних слоях (use cases / домен), реализации — во внешних адаптерах.
  - Для зависимости «наружу» вводится интерфейс в более внутреннем модуле и реализация во внешнем.

- **Фреймворки как детали, не как архитектура**  
  - Не наследовать доменные классы от базовых классов фреймворка.
  - Не размазывать аннотации фреймворка по сущностям и use case‑ам, где это не строго необходимо.
  - Фреймворк используется в слоях адаптеров и в точке входа (`main`, конфигурация), а не в домене.

- **Компоненты и стабильность (SDP / SAP)**  
  - **SDP (Stable Dependencies Principle)**: зависимости направлены в сторону более устойчивых компонентов.
  - **SAP (Stable Abstractions Principle)**: устойчивые компоненты должны быть абстрактными (интерфейсы, абстрактные классы).
  - Важные, редко меняющиеся решения (политики) — в устойчивых и абстрактных компонентах.

## Рабочий процесс при добавлении фичи

Используй этот чек‑лист, когда проектируешь или рефакторишь функциональность.

1. **Уточни сценарии использования (Use Cases)**  
   - Сформулируй действия на языке домена: «Пользователь логинится», «Приложение проверяет право доступа», «Подсистема получает токен».
   - Не думай пока о HTTP, БД, форматах сообщений.

2. **Выдели сущности и политики**  
   - Какие **сущности** участвуют? (User, Role, Permission, Session, Token, Subsystem, и т.п.)
   - Какие **инварианты** и правила должны выполняться всегда, независимо от технологий?

3. **Определи порты (интерфейсы) во внутренних слоях**  
   - Опиши интерфейсы для всего, что находится «за пределами» use case‑а:
     - хранилище (репозитории),
     - внешние сервисы,
     - генераторы идентификаторов/времени,
     - шифрование/хеширование.
   - Интерфейсы располагаются в модуле use case‑ов или домена, а не в инфраструктуре.

4. **Спроектируй адаптеры**  
   - Для каждого интерфейса определи одну или несколько реализаций во внешних модулях:
     - `DbUserRepository`, `JpaSubsystemRepository`, `HttpAuthClient` и т.п.
   - Контроллеры/ресурсы веб‑уровня вызывают **use case‑ы**, а не напрямую репозитории/ORM.

5. **Размести зависимости по слоям**  
   - Проверяй: домен и use case‑ы **не импортируют**:
     - классы Spring MVC / Wicket / JAX‑RS;
     - классы ORM (EntityManager, Session, аннотации JPA, и т.п.);
     - классы HTTP/серверов приложений.
   - Импорт таких классов допустим в:
     - контроллерах, фильтрах, конфигурации;
     - реализациях репозиториев, шлюзах к внешним системам.

6. **Минимизируй знание о фреймворках**  
   - Фреймворк помогает запускать приложение, но не диктует архитектуру.
   - Если фреймворк требует наследования/аннотации, изолируй это в адаптерах.

## Рефакторинг существующей кодовой базы

Когда код уже написан и нарушает правило зависимостей:

- **Шаг 1. Найди доменные правила, завязанные на инфраструктуру**  
  - Логика, использующая репозитории, HTTP‑объекты, аннотации фреймворков, перемешана в одном классе.

- **Шаг 2. Вытащи доменную часть в чистый сервис/use case**  
  - Перемести «чистую» бизнес‑логику в класс без зависимостей от фреймворков.
  - Внедряй внешние зависимости через интерфейсы.

- **Шаг 3. Введи интерфейсы и инвертируй зависимости (DIP)**  
  - Объяви интерфейсы во внутреннем модуле.
  - Реализуй их в существующих инфраструктурных классах и перемести эти классы во внешний модуль.

- **Шаг 4. Разруши циклы зависимостей между модулями**  
  - При цикле между модулями:
    - либо инвертируй одну из зависимостей через интерфейс;
    - либо выдели новый модуль с общей абстракцией.

## Паттерн «Порты и адаптеры» (гексагональная архитектура)

- **Порты** — интерфейсы, определяемые доменом/use case‑ами:
  - входные порты: интерфейсы сценариев (например, `LoginUseCase`, `IssueTokenUseCase`);
  - выходные порты: интерфейсы к БД, очередям, внешним сервисам.
- **Адаптеры** — реализации портов для конкретных технологий:
  - web‑контроллеры, UI, CLI — входные адаптеры;
  - репозитории, HTTP‑клиенты, gRPC‑клиенты — выходные адаптеры.
- Домен можно тестировать, подставляя фейковые (in‑memory) адаптеры.

## Примеры структурирования кода

### Пример 1. Use case с выходным портом

```java
// Внутренний модуль (use case)
public interface UserRepository {
    Optional<User> findByUsername(String username);
    void save(User user);
}

public class ChangePasswordUseCase {
    private final UserRepository userRepository;

    public ChangePasswordUseCase(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public void changePassword(String username, String newPasswordHash) {
        User user = userRepository.findByUsername(username)
                .orElseThrow(() -> new IllegalArgumentException("User not found"));
        user.changePasswordHash(newPasswordHash);
        userRepository.save(user);
    }
}
```

```java
// Внешний модуль (инфраструктура)
@Repository
public class JpaUserRepository implements UserRepository {

    private final EntityManager em;

    public JpaUserRepository(EntityManager em) {
        this.em = em;
    }

    @Override
    public Optional<User> findByUsername(String username) {
        // JPA / SQL детали
    }

    @Override
    public void save(User user) {
        // JPA / SQL детали
    }
}
```

### Пример 2. Web‑контроллер как адаптер

```java
// Веб-слой, зависит от use case, но не наоборот
@RestController
public class ChangePasswordController {

    private final ChangePasswordUseCase useCase;

    public ChangePasswordController(ChangePasswordUseCase useCase) {
        this.useCase = useCase;
    }

    @PostMapping("/users/{username}/password")
    public ResponseEntity<Void> changePassword(
            @PathVariable String username,
            @RequestBody ChangePasswordRequest body) {

        useCase.changePassword(username, body.getNewPasswordHash());
        return ResponseEntity.noContent().build();
    }
}
```

## Краткий чек‑лист

- **Зависимости внутрь**: домен и use case‑ы не зависят от UI, БД, фреймворков.
- **Интерфейсы внутри, реализации снаружи**.
- **Фреймворки — детали**: они находятся на внешнем слое и не просачиваются в домен.
- **Компоненты без циклов**: устранять циклы через DIP или выделение новых модулей.
- **Тестируемость**: домен и use case‑ы можно тестировать без запуска контейнера и БД.
