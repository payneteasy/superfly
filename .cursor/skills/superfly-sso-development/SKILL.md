# Разработка SSO в проекте Superfly

## Что такое Superfly

Superfly — центральный сервер единого входа (SSO) для организации:

- Регистрация пользователей, ролей и прав на центральном сервере.
- Интеграция со Spring Security; приложения могут использовать общую аутентификацию.
- **Redirect-режим**: пользователь один раз вводит пароль и перенаправляется в подсистемы с токеном.
- **No-redirect режим**: аутентификация через API без явного редиректа на страницу логина.
- Опциональная интеграция с Jira (управление правами из центра).

**Основные модули:**

- `superfly-web` — веб-интерфейс SSO (Wicket: страницы логина/логаута, OTP, настройка Google Authenticator), а также MVC API (например, remote auth).
- `superfly-spring-security` — провайдеры и фильтры аутентификации для Spring Security.
- `superfly-service` — бизнес-логика: сессии, подсистемы, токены, вызовы к хранилищу.
- `superfly-client` / `superfly-remote-api` — клиентская часть и API для проверки аутентификации подсистемами.

## Когда применять скиллы

- **Добавление или изменение эндпоинта аутентификации/проверки**  
  Применять скилл [secure-java-sso](.cursor/skills/secure-java-sso/): валидация ввода, сессии, cookie, токены, безопасные ответы об ошибках.

- **Выделение нового сервиса, смена хранилища или UI**  
  Применять скилл [clean-architecture-java](.cursor/skills/clean-architecture-java/): границы слоёв, зависимости внутрь, фреймворки (Spring, Wicket) во внешних адаптерах, порты и адаптеры.

## Типичные сценарии

- **Новый способ входа (например, OAuth/OIDC)**  
  Реализовать как порт/адаптер: домен и use case не зависят от протокола; адаптер преобразует запрос/ответ протокола в вызов use case. Это сохраняет возможность тестирования и смены протокола без переписывания домена.

- **Изменение политики сессий**  
  Централизовать создание и инвалидацию сессии, настройку cookie (path, HttpOnly, Secure, SameSite). Не дублировать логику в разных контроллерах/страницах.

- **Добавление или доработка MFA**  
  Оформить как отдельный шаг в потоке аутентификации (отдельная страница/эндпоинт после успешной проверки пароля). Не смешивать второй фактор с основным паролем в одном слое; проверки выполнять последовательно и безопасно (см. secure-java-sso).

## Существующие паттерны (сохранять и усиливать)

- **SSO-сессия в cookie**  
  Идентификатор сессии передаётся в cookie; сервер хранит состояние сессии и привязывает его к пользователю и правам.

- **Выдача subsystem token**  
  После успешного входа подсистема получает токен для доступа; проверка прав и подсистемы — в сервисном слое.

- **Remote auth API**  
  Эндпоинты вида `check-password`, `check-otp`: проверка Bearer-токена, согласованность username в path и body, явная проверка обязательных полей, единообразные коды ошибок (401, 400) без утечки внутренней информации.

- **Очистка сессии при неуспешном логине**  
  После неудачной аутентификации вызывать инвалидацию текущей SSO-сессии и удаление соответствующего cookie, чтобы исключить повторное использование старой сессии.

При доработках сохранять эти паттерны и усиливать их в соответствии с [secure-java-sso](.cursor/skills/secure-java-sso/) и [clean-architecture-java](.cursor/skills/clean-architecture-java/).
