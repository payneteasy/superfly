# Безопасность Java-приложений и SSO

## Когда применять этот скилл

- **Новый код аутентификации/авторизации**: эндпоинты логина, проверки пароля, OTP, выдачи токенов.
- **Работа с сессиями**: создание/инвалидация сессии, cookie, привязка к пользователю и правам.
- **Работа с данными**: запросы к БД, формирование ответов для клиента (риск инъекций, утечки данных).
- **Интеграция протоколов**: OAuth 2.0, OpenID Connect, SAML, защита redirect и state.
- **Секреты и конфигурация**: пароли, ключи, токены приложений.

## Ввод и вывод

- **Валидация ввода (allowlist)**  
  Проверять входящие данные по белому списку допустимых форматов и значений. Отклонять всё, что не соответствует. Не полагаться только на санитизацию «запрещённых» символов.

- **SQL / JPA**  
  Использовать только параметризованные запросы (`PreparedStatement`, именованные/позиционные параметры в JPA). Никогда не конкатенировать пользовательский ввод в строку запроса или в JPQL/HQL.

- **Вывод**  
  При отображении данных пользователю (HTML, JSON, логи) экранировать/кодировать в соответствии с контекстом (HTML-entity, JSON-escape, безопасное логирование без паролей и токенов).

## Аутентификация

- **Пароли**  
  - Минимум 8 символов при включённом MFA; 15+ символов без MFA.  
  - Запрещать общеизвестные и скомпрометированные пароли (проверка по списку/сервису).  
  - Хранить только хеш (стойкий алгоритм, соль); никогда не логировать и не возвращать пароль в ответах.

- **MFA**  
  Использовать многофакторную аутентификацию там, где это возможно; не смешивать второй фактор с основным паролем в одном «шаге» с точки зрения логики (отдельный шаг/эндпоинт).

- **Разделение схем**  
  Не использовать одну и ту же схему аутентификации для внутреннего (админского/сервисного) и публичного доступа. Разные механизмы или разные конфигурации (роли, политики).

## Управление сессиями

- **Идентификатор сессии**  
  Генерировать криптостойким ГПСЧ, достаточной длины; уникальный на пользователя/контекст. Не использовать предсказуемые значения (например, инкрементальные ID).

- **Привязка**  
  Сессия должна быть привязана к учётным данным и правам доступа; при смене пароля или отзыве прав — инвалидировать связанные сессии.

- **Таймаут**  
  Ограничивать время жизни сессии (абсолютный и неактивности); продлевать только при явной активности и повторной проверке контекста при необходимости.

- **Cookie**  
  Для идентификатора сессии использовать флаги: `HttpOnly`, `Secure` (при HTTPS), `SameSite` (Strict или Lax в зависимости от сценария). Путь — минимально необходимый (например, корень приложения).

- **После неуспешной аутентификации**  
  Очищать/инвалидировать текущую сессию и связанный cookie, чтобы не допустить повторного использования старой сессии после ошибки входа.

## OAuth 2.0 / OpenID Connect / SAML

- **PKCE**  
  Для публичных клиентов (SPA, мобильные приложения без секрета) использовать PKCE (Proof Key for Code Exchange).

- **CSRF**  
  Использовать `state` (OAuth) / `nonce` (OIDC), надёжно привязанные к пользовательскому агенту и проверяемые при обработке callback.

- **Redirect URI**  
  Строгая проверка: полное совпадение с зарегистрированным списком, без открытых редиректов и подстановки произвольного URI.

- **Транспорт**  
  TLS для всех обменов; для чувствительных утверждений (SAML) — подписание и при необходимости шифрование.

## Секреты

- Не хранить секреты в коде и в репозитории (никаких паролей, API-ключей, приватных ключей в коммитах).
- Использовать централизованное хранилище (переменные окружения, секрет-менеджер, vault) с минимальными правами доступа (принцип наименьших привилегий).
- Управлять жизненным циклом: ротация ключей и паролей, отзыв скомпрометированных значений.

## Токены и API аутентификации

- **Bearer-токен**  
  Проверять наличие и формат заголовка `Authorization: Bearer <token>`; при отсутствии или неверном формате возвращать 401 без раскрытия внутренних деталей.

- **Согласованность идентификаторов**  
  При приёме username/subsystem в path и в теле запроса проверять их совпадение и отклонять запросы с расхождением (например, 400 Bad Request).

- **Обязательные поля**  
  Явно проверять наличие обязательных полей (passwordEncrypted, sessionToken, otpEncrypted и т.п.) и возвращать понятную ошибку (400), а не падение или неопределённое поведение.

- **Ошибки**  
  Обрабатывать ошибки единообразно: не возвращать в ответе стек-трейсы, внутренние пути, версии БД/сервера. Логировать детали на сервере; клиенту — код ошибки и короткое сообщение (например, тип и errorId для трассировки).

## Краткий чек-лист

- [ ] Ввод: allowlist-валидация; параметризованные запросы к БД/JPA.
- [ ] Вывод: экранирование в контексте вывода.
- [ ] Пароли: длина, MFA, хеш, запрет утечек; не логировать.
- [ ] Сессия: криптостойкий ID, привязка, таймаут, cookie (HttpOnly, Secure, SameSite), инвалидация после неуспешного входа.
- [ ] OAuth/OIDC: PKCE для публичных клиентов, state/nonce, проверка redirect_uri, TLS.
- [ ] Секреты: не в коде; централизованное хранилище; наименьшие привилегии.
- [ ] API: проверка Bearer, согласованность path/body, обязательные поля, безопасные сообщения об ошибках.
